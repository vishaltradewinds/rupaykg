4. `004_security_auth.sql` — organization memberships and opaque identity sessions.
5. `005_carbon_epr_esg.sql` — carbon projects/calculations, EPR and ESG reporting records.
6. `006_registry_settlement_guardrails.sql` — database-level issuance and settlement safety guards.
7. `007_resource_flow_mrv.sql` — resource custody links and MRV observation/verification requirements.
8. `008_verification_integrity.sql` — independent verifier authorization and verification integrity controls.
9. `009_field_sync.sql` — durable offline field envelopes, conflicts and cursors.

16. `016_field_device_enrollment.sql` — field-device enrollment and lifecycle controls.

18. `018_value_mutation_permissions.sql` — authorization boundaries for value-layer mutations.
19. `019_settlement_reconciliation_immutability.sql` — immutable settlement reconciliation evidence and state controls.
20. `020_carbon_calculation_provenance.sql` — evidence-bound carbon calculation provenance.
21. `021_methodology_governance.sql` — methodology source lock, applicability/parameter/equation mapping and production-eligibility governance.
22. `022_carbon_provenance_integrity.sql` — database integrity controls for carbon provenance.

27. `028_settlement_retired_credential_guard.sql` — prevents settlement creation for retired credentials and prevents retirement while an attached settlement remains open.

Migration `023` is intentionally absent from the current repository history; do not renumber later migrations to fill the gap. Migration numbering is identity, not a requirement for contiguous integers.

Migration files are intentionally ordered and each numbered migration must have one authoritative owner. Do not reintroduce duplicate numbered migrations containing the same tables or enums.

## Production rule

A migration runner must stop on the first error. Never silently continue after a partial schema application. Run against a controlled migration ledger in deployment infrastructure before accepting application traffic.

Verification requires a verified organization membership with an explicit `VERIFY_EVIDENCE` permission (or one of its documented aliases). Role names such as `VERIFIER`/`AUDITOR` are not privilege grants, and an activity actor cannot approve their own evidence. Registry and settlement event hashes are generated by PostgreSQL from canonical event fields rather than trusting caller-provided hashes.

## Field-sync application rule

Receiving an offline envelope does not mutate authoritative business state. An envelope is applied only through an explicit authenticated application step. Supported operation types are deliberately allow-listed: `ACTIVITY_CREATE`, `MEASUREMENT_CREATE`, `EVIDENCE_CREATE`, and `RESOURCE_FLOW_CREATE`. The domain mutation and envelope status change commit in the same database transaction; failures roll back both.

## Geography authorization rule

An organization may have explicit verified geography roots. When roots exist, activities and resource flows are accepted only when their geography is the assigned root or a descendant of an assigned root. This is enforced in PostgreSQL so API and offline paths cannot bypass the authorization boundary. Organizations without configured geography roots remain governed by their existing organization-membership authorization until scopes are provisioned.

## Settlement truth rule

A settlement may enter `SETTLED` only when the authoritative settlement record contains an external settlement reference, an external-authority confirmation timestamp, and a reconciliation reference. These fields cannot be cleared after confirmation. Internal workflow transitions alone must never be treated as proof that funds moved.

A credential in `RETIRED` state cannot be used to create a settlement. A credential cannot be retired while it has an open settlement (`CREATED`, `AUTHORIZED`, `EXECUTING`, or `RECONCILING`). These lifecycle constraints are enforced at the PostgreSQL boundary rather than relying only on HTTP route behavior.

## Guardian/Hedera registry acceptance migration

Migration `083_mrv_mirror_node_registry_gate.sql` adds the persisted `mirror_node_verified_at` acceptance marker and tightens the PostgreSQL credential-issuance trigger. A Guardian `VERIFIED` result and Hedera `CONSENSUS_CONFIRMED` response are not sufficient by themselves; the exact anchored payload must also be successfully verified through Mirror Node. Existing provenance rows remain ineligible until that verification is performed. The authenticated Mirror Node verification endpoint checks the exact payload/hash and persists the marker only if the anchored tuple has not changed during verification. Credential issuance requires that persisted marker, and PostgreSQL independently checks it on inserts and transitions into value-bearing credential states.

## Platform-admin audit chain head

Migration `084_platform_audit_chain_head.sql` bootstraps a singleton chain head using the latest existing audit row as a migration-time anchor. Older audit writers do not all participate in the platform-admin chain, so the bootstrap is not a certification of the entire historical audit table. After cutover, platform-admin appends lock the head row inside the same transaction, use its hash as the predecessor, insert the event, and advance the head atomically. Append order therefore does not depend on transaction-start timestamps or random UUID ordering. A failed transaction rolls back both event and head update. Audit events are append-only; tests must not delete them or rewind the head.

## Reserved-role dual control

Migration `085_platform_access_dual_control.sql` records requests to grant reserved platform roles or restore a revoked reserved-role membership. The request and decision are separately authenticated, require distinct active Super Admin requester and approver identities, prohibit the target identity from approving its own change, revalidate the target and role at decision time, apply the membership change in the same transaction as approval, and append a hash-linked audit event. Ordinary membership grant and restoration routes remain blocked for reserved roles.


## Reserved-role restoration guard

Migration `086_reserved_role_restoration_db_guard.sql` protects status reactivation of a revoked `super_admin` or `platform_admin` membership. It requires a matching approved dual-control request, a different requester and approver, a target distinct from both, active Super Admin authority for requester and approver, and a request created after the revocation. Ordinary reserved-role grant/restoration APIs remain blocked; new grants are applied only by the authenticated dual-control workflow. Initial Super Admin bootstrap is an out-of-band privileged provisioning step and is not exposed through the ordinary API.


## Acceptance fixture registry exclusion

Migration `087_acceptance_fixture_registry_exclusion.sql` prevents activities or evidence explicitly marked with `metadata.acceptanceFixture=true` from backing credentials in value-bearing states. It also binds the database gate to the exact activity, verification, and evidence tuple. The MRV API reports acceptance fixtures as not registry eligible even after real Guardian/Hedera/Mirror Node verification. External anchoring proves message integrity and consensus; it does not validate the underlying activity as a real eligible carbon project.


## Government inbox worker (migration `20261023_async_mirror_worker_leases.sql`)

The government bridge inbox now has a one-shot worker runner exposed as `npm run worker:gov-inbox -w @rupaykg/api` after the API workspace has been built. Schedule it through the deployment platform's authenticated job/cron facility; do not expose the runner as a public HTTP route. The job uses the same validated production database configuration and emits aggregate counts only.

The worker claims a bounded batch with PostgreSQL `FOR UPDATE SKIP LOCKED`, uses a lease token as a fencing condition on state updates, applies capped exponential retry for transient errors, quarantines exhausted work, and offers read-only reconciliation counts. A structurally valid batch is recorded as `VALIDATED` only after exactly one effective VERIFIED jurisdiction crosswalk is resolved and explicit organization geography scope is rechecked. A structurally valid batch with no or ambiguous mapping is recorded as `UNRESOLVED`; malformed payloads are `REJECTED`. None of these internal statuses is official government acceptance or verified MRV, and none changes authoritative measurements, submits to Guardian/Hedera, or creates a carbon credit.

**Deployment gate:** this commit adds the worker and invocation command, but does not create a live scheduler or run it against production data. Configure a scheduled job only after the migration is applied to the target database and its least-privilege access, logs, alerting, retry behavior and rollback have been verified in staging. Do not configure an authority source until CPCB's official integration contract and authorization are confirmed.


## AI evidence-intake rate limit (migration `20261024_ai_intake_rate_limits.sql`)

The AI evidence-intake route uses a PostgreSQL-backed fixed-window counter keyed by identity, organization and database minute. The atomic upsert permits at most 10 attempts per identity/organization/minute across multiple API instances; over-limit requests receive HTTP 429 before evidence persistence or model-provider invocation. Counters contain no source payloads. This migration is not part of production's currently applied migration set; apply only through the reviewed migration process after staging validation. Rate limiting is not idempotency, job persistence, or monitoring.

## AI evidence-intake idempotency and recovery (migration `20261025_ai_evidence_intake_jobs.sql`)

The evidence-intake endpoint requires an `Idempotency-Key` header (1–200 characters). The ledger scopes keys to authenticated identity and organization and stores a SHA-256 digest of the normalized request identity (activity, source log, and source reference), never the raw log. Reusing a key with different content returns HTTP 409. A completed request replays the saved response; a currently leased request returns HTTP 202; retryable or expired work can be reclaimed with a new fencing token. Source evidence ID is linked in the same transaction that captures the original evidence, preventing a retry from creating a second source artifact. Proposal persistence and completion state commit together.

This ledger is **not yet production-applied**. Before enabling this route in any environment, apply migrations `20261024` and `20261025` in order through the controlled migration runner, run `intelligence-idempotency-db.test.ts` against disposable PostgreSQL and add endpoint-level coverage for provider failures, actual HTTP response replay/conflict behaviour and process restarts; verify recovery/monitoring. The database integration test covers concurrent same-key creation, changed-content distinguishability, expired-lease takeover, stale-token fencing, retryable failure/recovery and durable completed-response storage. It does not substitute for endpoint-level HTTP tests. The worker lease is five minutes; provider timeouts must remain below that lease or lease renewal must be added before allowing longer jobs. Do not run these migrations on production as part of this draft change.


## Organization-to-stakeholder authorization dual control (migration `20261027_stakeholder_authorization_dual_control.sql`)

Stakeholder mappings can be verified or revoked only through an evidence-backed request and a separate approval by a different active Super Admin. `request_action=VERIFY` binds the approved evidence and expiry to the mapping; `request_action=REVOKE` changes the currently verified mapping to REVOKED only after independent approval. The database trigger rejects direct VERIFIED mapping inserts/updates without a matching approved request, with matching organization/stakeholder, distinct requester and approver, matching reviewer identity, and unexpired request. Request creation and decision require a reason and evidence reference plus SHA-256; approval and mapping persistence plus audit-chain append are atomic. This is an internal platform gate, not proof of CPCB registration or statutory authority. Do not populate real mappings until the reviewer mandate and evidence acceptance policy are approved under Shakti Standards.


## CPCB SWM workspace geography requirement (migration `20261029_cpcb_swm_workspace_geography_required.sql`)

New CPCB SWM workspace inserts and explicit geography changes must provide a geography ID. The API and database trigger require an explicit verified organization geography root that contains the requested geography; the API also requires a verified organization membership. Existing legacy rows with NULL geography are not rewritten; they remain a migration/backfill review item. Validate this migration against disposable PostgreSQL and inspect legacy row counts before any production application. This guard is scoped to the CPCB SWM workspace table; other high-risk workflows require their own reviewed scope enforcement.

## Strict geography authorization for high-impact workflows (migration `20261030_explicit_geography_scope.sql`)

The legacy `organization_has_geography_scope` helper intentionally permits organizations with no verified roots for compatibility. That fallback is not sufficient for high-impact operations. The new `organization_has_explicit_geography_scope` helper requires at least one verified organization geography root and confirms the requested geography is within that root. MRV submission, EPR return submission, statutory evidence binding, and value-layer geography/evidence checks now use the strict helper. Disposable PostgreSQL acceptance coverage verifies that an organization without roots is denied and an explicitly scoped geography is accepted. Existing unscoped tenants are not auto-assigned a jurisdiction; they must be reviewed and provisioned before using these high-impact workflows.

## Government jurisdiction crosswalk foundation (migration `20261031_government_jurisdiction_crosswalk.sql`)

This migration creates a versioned, evidence-backed crosswalk from authority/municipal source identifiers to a RupayKg organization and canonical geography, with an optional activity binding. It creates **no real authority mappings** and does not infer official identifiers. A mapping is PENDING by default; VERIFIED rows require evidence reference/hash, a separate approving identity, an approval reason, a verification timestamp, and an explicitly scoped geography. The database rejects an optional activity binding if its organization or geography differs. A unique verified key prevents one source identifier/version from silently resolving to multiple tenants or geographies.

This is a schema foundation, not a completed government integration. The reviewed core schema has no single canonical site entity to bind here, so the migration intentionally does not invent a polymorphic site ID. Before the government inbox worker consumes crosswalks, add an authenticated request/approval workflow that checks the approver's authority, test ambiguity/expiry/revocation and source-version changes, and wire the worker to fail closed when no unique currently effective VERIFIED crosswalk exists. Do not seed production mappings until authoritative source records and reviewer evidence are available.

## Government jurisdiction crosswalk (migration `20261031_government_jurisdiction_crosswalk.sql`)

This migration maps an external authority/municipal identifier and source version to a tenant organization, canonical geography, and optionally a specific activity. It records evidence reference and SHA-256, effective dates, and request/approval provenance. VERIFIED mappings require an exact approved request, matching organization/geography/activity and evidence, distinct requester and approver, explicit verified organization geography scope, and a source-versioned canonical geography target. An external identifier must remain unresolved if it cannot be mapped unambiguously.

The request lifecycle is constrained to creation as PENDING followed by one decision to APPROVED or REJECTED; request-defining fields are immutable after creation. The registered API routes require organization-level stakeholder-management permission to request a mapping and an active Super Admin with platform-management permission to decide it; requester self-approval is rejected. Approval and mapping persistence occur in one transaction and append to the platform audit chain. This schema does not seed official identifiers, infer LGD mappings, or itself prove government authorization. The inbox worker does not yet consume the crosswalk, and end-to-end batch-to-organization/site/activity binding remains a separate release gate. CI and disposable-PostgreSQL acceptance are pending for the latest route/test head.

## Unresolved government bridge batches (migration `20261101_async_mirror_unresolved_crosswalk.sql`)

A structurally valid government inbox batch is not marked internally `VALIDATED` unless its authority/municipal identifiers resolve to exactly one currently effective, VERIFIED `government_jurisdiction_crosswalks` record and that organization's explicit geography scope still authorizes the canonical geography. The worker records the crosswalk ID, organization, geography and source version in the non-authoritative validation summary. It explicitly records `domainBinding=NOT_PERFORMED`; it does not mutate activities, measurements, evidence, MRV calculations, Guardian/Hedera or carbon-credit records.

If no mapping exists or more than one mapping matches the batch's effective timestamp, the batch enters `UNRESOLVED` for review rather than being misclassified as malformed or retried until quarantine. This is an internal routing state only, not official acceptance/rejection. Do not enable a live authority adapter until its source identifiers, payload contract, and crosswalk evidence have been verified.


## Regulatory rule source-scope gate (migration `20261106_regulatory_rule_source_gate.sql`)

A regulatory rule cannot be marked `APPROVED` unless its source snapshot is already `APPROVED`, its source jurisdiction is compatible with the rule jurisdiction (a national source may support a narrower rule; narrower or unrelated sources may not silently support broader rules), and the rule's effective period fits within the source snapshot's effective period. Non-national jurisdiction scope codes must match exactly unless a separate reviewed crosswalk establishes a supported relationship. This is an internal provenance control, not a legal determination, statutory approval, or evidence that the source dataset is complete for India. Do not seed nationwide rules or snapshots without verified source material, coverage counts, usage terms, and named review.


## Approved source snapshot immutability (migration `20261107_approved_source_snapshot_immutability.sql`)

Once an authoritative source snapshot is approved, its source owner, dataset/version, URL, jurisdiction scope, publication/retrieval and effective dates, content hash, coverage counts, usage-terms reference, and reviewer provenance cannot be rewritten. Corrected source material must be captured as a new snapshot/version. Lifecycle status and explanatory notes remain separately mutable; retiring a snapshot is not itself proof that every historical rule or filing is invalid. This protects source provenance from silent edits and does not establish nationwide coverage or legal approval.


## Crosswalk request expiry immutability (migration `20261108_crosswalk_request_expiry_immutability.sql`)

A crosswalk request's `expires_at` cannot be changed after creation, including in the same update that approves or rejects the request. The API rejects expired approvals with `GOVERNMENT_CROSSWALK_REQUEST_EXPIRED`; the database trigger prevents extending an expired request to bypass that check. Submit a new evidence-backed request instead. This is an internal integrity control, not official authority approval.


## Source snapshot authority identity and terminal retirement (migration `20261109_source_snapshot_retirement_terminal.sql`)

An approved source snapshot's `authority_code` is part of its immutable provenance. Approved snapshots may remain approved or be retired; they cannot be downgraded to rejected or another status. Retired snapshots are immutable and terminal, and cannot be re-approved or moved to another status. Corrected or replaced data must be recorded as a new source snapshot/version with its own review. Worker resolution additionally requires the bound snapshot to remain APPROVED for new inbox batches. Integration coverage checks authority-code tampering, post-retirement tampering and re-approval attempts. These are internal provenance controls, not official authority approval or proof of dataset completeness.


## External settlement confirmation gate

The settlement confirmation API is intentionally fail-closed while no independently authenticated external settlement confirmation adapter is configured. Caller-supplied confirmation/reconciliation reference strings are not proof that funds moved; the API leaves the record in `RECONCILING` and does not set `external_confirmed_at` or `SETTLED`. Do not enable settlement finalization until a trusted provider adapter validates the provider event and reconciliation evidence, with its own integration tests and operational controls.


## Failed settlement terminal-state correction (2026-11-10 migration sequence)

Migration `20261110_failed_settlement_terminal_for_retirement.sql` aligns the database retirement guard with the API: a settlement in `FAILED` is terminal and no longer treated as an open settlement that blocks credential retirement. `CREATED`, `AUTHORIZED`, `EXECUTING`, and `RECONCILING` remain open; `SETTLED`, `CANCELLED`, and `FAILED` are terminal for retirement and transfer guards and are excluded from active-settlement uniqueness. This does not make a failed settlement evidence that funds moved.


## CPCB SWM strict geography guard (2026-11-11 migration sequence)

Migration `20261111_cpcb_swm_strict_geography_guard.sql` aligns the PostgreSQL trigger with the strict helper used by the CPCB SWM API routes. Inserts and geography changes require an explicit verified organization geography root and a requested geography within that root. The legacy geography helper remains available for lower-risk legacy workflows; this migration does not globally change its semantics.


## Pan-India geography identifier crosswalk foundation (2026-11-12 migration sequence)

Migration `20261112_geography_external_identifiers.sql` adds a provenance-bound alias registry that maps an official source's identifier to a stable internal geography record without treating source codes as RupayKg primary keys. Each mapping carries its source version, identifier type, effective period, review identity/time, HTTPS source reference and SHA-256 source checksum. Verified mappings with overlapping effective periods for the same source/type/code are rejected by a PostgreSQL GiST exclusion constraint, including concurrent writes. Verified mappings are immutable except for one-way retirement. No official geography data is seeded by this migration, and a strict SQL resolver is provided for exact source/type/code/effective-date lookups, but existing routing does not automatically consume these aliases yet. Before production use, add official-source ingestion/reconciliation, reviewed snapshots, representative state/district/local-body coverage, resolver integration and migration-level integration tests. This is a schema foundation, not evidence of Pan-India coverage or government endorsement.


## Government crosswalk resolver integration (2026-11-13 change)

The government jurisdiction crosswalk request API can optionally accept `externalIdentifierType`. When supplied, the request must resolve `municipalCode` using the exact verified source identifier for which the approved source snapshot, geography source URL, source version and SHA-256 content checksum match. The resolver must return the same canonical geography ID submitted by the requester; absent, ambiguous, stale or mismatched aliases fail closed. Requests without this optional field continue through the existing evidence-backed, dual-control review path; they are not silently auto-mapped. This does not seed official aliases or establish nationwide coverage.

## Strict Pan-India geography authorization

Migration `012_geography_authorization.sql` retains the legacy `organization_has_geography_scope` no-root fallback for compatibility; that helper must not be treated as sufficient authorization for high-impact workflows. Migration `20261030_explicit_geography_scope.sql` adds `organization_has_explicit_geography_scope`, which requires a non-null requested geography, at least one VERIFIED organization geography root, and ancestry containment. The high-impact activity and resource-flow database guards in `20261114_strict_activity_geography.sql` and `20261113_strict_resource_flow_geography.sql` require explicit scope and reject missing geography on new or changed records. Existing rows are not rewritten by these guards and require a separately planned, evidence-backed backfill before any stronger read or release assertion.

Regression acceptance must cover missing geography, an unscoped organization, a valid in-scope geography, and an unrelated geography. Run the PostgreSQL tests only against disposable CI/staging data; do not use cleanup that deletes or rewinds inherited production records.
