Migration files are intentionally ordered and each numbered migration must have one authoritative owner. Do not reintroduce duplicate numbered migrations containing the same tables or enums.

## Production rule

A migration runner must stop on the first error. Never silently continue after a partial schema application. Run against a controlled migration ledger in deployment infrastructure before accepting application traffic.

Verification requires a verified organization membership with an explicit `VERIFY_EVIDENCE` permission (or one of its documented aliases). Role names such as `VERIFIER`/`AUDITOR` are not privilege grants, and an activity actor cannot approve their own evidence. Registry and settlement event hashes are generated by PostgreSQL from canonical event fields rather than trusting caller-provided hashes.

## Field-sync application rule

Receiving an offline envelope does not mutate authoritative business state. An envelope is applied only through an explicit authenticated application step. Supported operation types are deliberately allow-listed: `ACTIVITY_CREATE`, `MEASUREMENT_CREATE`, `EVIDENCE_CREATE`, and `RESOURCE_FLOW_CREATE`. The domain mutation and envelope status change commit in the same database transaction; failures roll back both.

## Geography authorization rule

An organization may have explicit verified geography roots. When roots exist, activities and resource flows are accepted only when their geography is the assigned root or a descendant of an assigned root. This is enforced in PostgreSQL so API and offline paths cannot bypass the authorization boundary. Organizations without configured geography roots remain governed by their existing organization-membership authorization until scopes are provisioned.

## Settlement truth rule

A settlement may enter `SETTLED` only when the authoritative settlement record contains an external settlement reference, an external-authority confirmation timestamp, and a reconciliation reference. These fields cannot be cleared after confirmation. Internal workflow transitions alone must never be treated as proof that funds moved.

A credential in `RETIRED` state cannot be used to create a settlement. A credential cannot be retired while it has an open settlement (`CREATED`, `AUTHORIZED`, `EXECUTING`, or `RECONCILING`). These lifecycle constraints are enforced at the PostgreSQL boundary rather than relying only on HTTP route behavior.

## Guardian/Hedera registry acceptance migration

Migration `083_mrv_mirror_node_registry_gate.sql` adds the persisted `mirror_node_verified_at` acceptance marker and tightens the PostgreSQL credential-issuance trigger. A Guardian `VERIFIED` result and Hedera `CONSENSUS_CONFIRMED` response are not sufficient by themselves; the exact anchored payload must also be successfully verified through Mirror Node. Existing provenance rows remain ineligible until that verification is performed. The authenticated Mirror Node verification endpoint checks the exact payload/hash and persists the marker only if the anchored tuple has not changed during verification. Credential issuance requires that persisted marker, and PostgreSQL independently checks it on inserts and transitions into value-bearing credential states.

## Platform-admin audit chain head

Migration `084_platform_audit_chain_head.sql` bootstraps a singleton chain head using the latest existing audit row as a migration-time anchor. Older audit writers do not all participate in the platform-admin chain, so the bootstrap is not a certification of the entire historical audit table. After cutover, platform-admin appends lock the head row inside the same transaction, use its hash as the predecessor, insert the event, and advance the head atomically. Append order therefore does not depend on transaction-start timestamps or random UUID ordering. A failed transaction rolls back both event and head update. Audit events are append-only; tests must not delete them or rewind the head.

## Reserved-role dual control

Migration `085_platform_access_dual_control.sql` records requests to grant reserved platform roles or restore a revoked reserved-role membership. The request and decision are separately authenticated, require distinct active Super Admin requester and approver identities, prohibit the target identity from approving its own change, revalidate the target and role at decision time, apply the membership change in the same transaction as approval, and append a hash-linked audit event. Ordinary membership grant and restoration routes remain blocked for reserved roles.


## Reserved-role restoration guard

Migration `086_reserved_role_restoration_db_guard.sql` protects status reactivation of a revoked `super_admin` or `platform_admin` membership. It requires a matching approved dual-control request, a different requester and approver, a target distinct from both, active Super Admin authority for requester and approver, and a request created after the revocation. Ordinary reserved-role grant/restoration APIs remain blocked; new grants are applied only by the authenticated dual-control workflow. Initial Super Admin bootstrap is an out-of-band privileged provisioning step and is not exposed through the ordinary API.


## Acceptance fixture registry exclusion

Migration `087_acceptance_fixture_registry_exclusion.sql` prevents activities or evidence explicitly marked with `metadata.acceptanceFixture=true` from backing credentials in value-bearing states. It also binds the database gate to the exact activity, verification, and evidence tuple. The MRV API reports acceptance fixtures as not registry eligible even after real Guardian/Hedera/Mirror Node verification. External anchoring proves message integrity and consensus; it does not validate the underlying activity as a real eligible carbon project.


## Signed tenant request context verifier

**DBA prerequisite before applying migration `20261101_signed_request_context_verifier.sql`:** provision `rupaykg_security_definer` as `NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOINHERIT NREPLICATION`. Grant it `CREATE` on the target database and grant membership only to the dedicated migration principal so the migration can `SET LOCAL ROLE`. Do not grant membership to the API runtime, authentication runtime, worker, or user-facing roles. The role must not own tenant application tables and must not inherit from a BYPASSRLS role. The migration fails closed if the role is absent or has any forbidden attribute. CI provisions this role only inside its disposable PostgreSQL service.


Migration `20261101_signed_request_context_verifier.sql` creates the restricted `app_security` schema, protected HMAC key table and a `SECURITY DEFINER` verifier for short-lived signed request-context envelopes. The verifier validates actor UUID, organization UUID, issue/expiry times, key ID and HMAC-SHA256 signature; malformed, expired, unknown-key and forged contexts return NULL. The function pins its search path and the key table/function are not executable/readable by PUBLIC.

This migration intentionally grants no privileges to application roles. A dedicated NOBYPASSRLS runtime role must be provisioned separately and receive only `USAGE` on `app_security` and `EXECUTE` on the verifier. The runtime role must not receive SELECT on the key table. The signing secret must be provisioned out-of-band and rotated by key ID. This verifier alone does not enable RLS or authorize tenant data; policies on each application table must consume its verified claims.


## One-time platform authority bootstrap (20261102)

This migration installs a **draft-only, one-time two-custodian bootstrap path**. It does not provision real identities, secrets or custodian logins.

### Required DBA preconditions
- Pre-provision `rupaykg_bootstrap_owner` as NOLOGIN, NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE, NOINHERIT and NOREPLICATION.
- Temporarily grant that role CREATE on the authoritative database and grant membership with SET permission to the migration principal. The migration revokes the database CREATE privilege after creating its private schema.
- The migration creates `rupaykg_bootstrap_custodian` as a NOLOGIN capability role with no outbound memberships and only EXECUTE on the two bootstrap functions.
- After migration, provision exactly two distinct LOGIN custodian roles, both NOINHERIT/NOBYPASSRLS and with no elevated attributes or other role memberships. Grant each membership in `rupaykg_bootstrap_custodian` with `INHERIT FALSE, SET TRUE`. The migration does not create production custodian login credentials.

### Ceremony protocol
1. Founder selects two distinct identities already VERIFIED by the trusted identity process.
2. Founder/DBA creates one time-limited ceremony and exactly two claims, each binding one identity to one custodian login role and a SHA-256 hash of a high-entropy single-use secret. Raw secrets are never stored.
3. Each custodian independently connects using their own login role, executes `SET ROLE rupaykg_bootstrap_custodian`, and submits only their own secret through `bootstrap_private.submit_initial_platform_authority_claim`.
4. After both claims are accepted, either custodian calls `bootstrap_private.finalize_initial_platform_authority_bootstrap`. The function atomically creates the platform authority organization and exactly two initial Super Admin memberships, consumes both claims and the ceremony, and writes a separate append-only hash-linked bootstrap audit event.
5. The membership trigger exception is accepted only while the singleton bootstrap state is CONSUMING, only for the exact platform authority organization/role and the two claimed identities, and only when both independent custodian submissions are present. The ordinary approved-application and reserved-role dual-control guards remain in force for all other writes.

### Security boundaries
- Bootstrap functions are SECURITY DEFINER under the dedicated NOLOGIN/NOBYPASSRLS owner, have pinned search_path, and are not executable by PUBLIC or application runtime roles.
- Custodian capability has no table access; it can only execute the two narrow functions. The login roles are separately bound to identity claims and must be distinct.
- The bootstrap state is globally one-time. Reused, expired, cross-custodian, missing or malformed secrets fail closed.
- CI uses synthetic identities and synthetic custodian login roles only. No production identities, secrets, claims or logins are created by this migration.
- Production execution remains blocked until the founder approves the two initial identities and the out-of-band two-custodian secret-custody ceremony, and independent security review passes.


## Read-only EPR returns tenant RLS (20261110)

Migration `20261110_epr_return_read_tenant_rls.sql` is a candidate, not a production deployment. It requires a separately provisioned `rupaykg_app_runtime` LOGIN role with NOBYPASSRLS, NOINHERIT, no elevated attributes and no role memberships. The migration grants that role SELECT only on `public.epr_returns` and the global `public.epr_schemes` catalogue, gives it verifier schema/function use but no signing-key table read, and enables/forces a single organization-claim SELECT policy on `public.epr_returns`.

The API route is disabled by default through `RUPAYKG_EPR_RETURN_READ_ENABLED=false`. When explicitly enabled, startup checks the actual connection identity, RLS/FORCE RLS, exact policy, table ownership, read-only privileges and verifier ownership/grants before registering only `GET /api/v1/epr/returns`. The route uses the existing explicit `withRlsRequestTransaction` client boundary; authentication occurs first, then permission lookup and EPR row reads use the same signed tenant client. No EPR write route is registered.

This migration must be rehearsed on disposable PostgreSQL with the exact restricted runtime role and two-tenant negative tests. Production migration, role/secret provisioning and feature activation remain blocked pending independent DBA/security approval and explicit founder authorization.


## Verifier active-identity and tenant trigger guard (20261111)

Migration `20261111_verifier_active_identity_and_trigger_tenant_guard.sql` closes verifier authorization gaps across **both** active BEFORE INSERT/UPDATE trigger entry points on `public.verifications`: `verifications_integrity_guard` → `prevent_invalid_verification()` and `verification_independence_guard` → `enforce_verification_independence()`. Both functions now delegate to the same fail-closed activity authorization predicate. The predicate requires an active `VERIFIED` identity, a `VERIFIED` membership in the subject activity's organization, a `VERIFIED` subject organization, an explicit verification permission (`verification:approve`, `verification.approve`, or the legacy `VERIFY_EVIDENCE` alias), and a matching `VERIFIED` geography scope. Role labels alone do not grant verification authority.

Both trigger functions resolve the subject activity from the verification row or its evidence, reject mismatched activity/evidence pairs, check self-verification first, and apply the same tenant-bound predicate to every decision. The integration test asserts the actual trigger-to-function bindings and exercises same-tenant success, foreign-tenant denial for APPROVED and REJECTED, role-label-only denial, suspended/unverified identity, pending membership, unverified organization, pending geography scope, and self-verification.

This is a forward-only candidate migration on a review branch. It has not been applied to production. CI must apply the full migration chain to disposable PostgreSQL and pass the behavioral trigger matrix. The migration's SQL definition alone is not certification evidence.


## Stakeholder platform-authority approval guard (20261112)

Migration `20261112_stakeholder_platform_authority_scope.sql` replaces the stakeholder-application approval trigger's global role-name lookup. An approval transition now requires the reviewer identity to be active and `VERIFIED`, the membership to be `VERIFIED`, the membership's organization to be `VERIFIED` and of type `PLATFORM_AUTHORITY`, and the role to be `platform_admin` or `super_admin` with an explicit `admin:users` permission. Self-approval and direct INSERT as `APPROVED` remain prohibited. The function is SECURITY INVOKER and pins `search_path`.

The PostgreSQL integration test rejects approval by a verified ordinary-tenant verifier and accepts approval by the synthetic active platform authority. The shared onboarding fixture now discovers only a reviewer meeting the same platform-authority and explicit-permission predicate. This is a candidate migration only; disposable PostgreSQL acceptance and independent security review are required before any production change.


## Application-owned routine search-path hardening (20261113)

Migration `20261113_pin_application_function_search_paths.sql` pins every application-owned public function/procedure to `pg_catalog, public, pg_temp`, excluding extension-owned routines so extension lifecycle remains controlled by the extension. The current production catalog shows PUBLIC has USAGE but not CREATE on public; pg_temp is placed last to prevent temporary-object shadowing. The integration test checks every application-owned public routine has exactly the reviewed path and confirms PUBLIC has no CREATE privilege on public.

This is a candidate migration. CI must apply the full chain and pass all existing trigger, function, route, PostgreSQL acceptance and production-container gates. It does not revoke PUBLIC EXECUTE: a separate signature/call-site/grant inventory is required first, especially because trigger functions and ordinary helper functions have different invocation semantics. No production routine has been altered by this candidate.
